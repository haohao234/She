# 她的信息本 · iOS 起步骨架

这份代码是**设计稿到 iOS 之间的桥**，不是成品 App。

它的用途有两个：一是让工程师不用从零猜设计意图，二是**反过来验证设计能不能落地** ——
有些决策（比如地理围栏只能绑 20 个点、中文该用系统字体还是捆绑 Noto）只有在写代码时才会浮出来，
它们已经被写回设计说明里。

## 一、怎么跑起来

（契约文件少勾一个 target、App Group 少开一边、扩展 bundle id 没挂到主 App 下）
在这份声明里是结构性的，漏不了。

2. 等 1–5 分钟，看 Actions 是绿的还是红的

> **失败时不用你翻日志。** 把「失败了」告诉我，我这边能直接取到完整构建日志
> 并摘出 error 行（公开仓库的日志接口要权限，本机已存的 GitHub 凭据够用）。
> 你也可以自己看：Actions → 那一次运行 → 点开「摘出错误与警告」那一步。

> **本地仓库已就绪**（分支 `main`，远程地址已配好）。
> 逐步操作、每一步的验证点与坑，看 **`她的信息本-iOS编译操作指引.html`**。

> **这台机器到 github.com 的连接时通时断 —— 脚本会自己重试。**
> 实测：`git ls-remote` 报 `Failed to connect to github.com:443 after 21033 ms:
> Could not connect to server`，几分钟后原样重跑就通了。
> 脚本 v5 在「测地址」和「推送」两处都加了自动重试（网络类失败等 4–5 秒重来，
> 最多 3 次），三次都不通才报「网络不通」，并且不会再把用户引向
> 「去改地址 / 重新登录」那种完全错误的方向。

> **`git` 能读不能写，根因不在网络，在凭据链（v5 修掉的真凶）。**
> `git ls-remote` 是匿名读取、不需要凭据，所以秒过；`git push` 要认证**两次**
> （取一次、存一次），而系统级 gitconfig 里的 `credential.helper = helper-selector`
> 每次认证都要**空跑 40 秒 ×2**，命令在超时线上被掐死，**屏幕上一个字都不打** ——
> 现场看着就是「网络不通」。
>
> 关键机关是：**`credential.helper` 是【累加】的，不是覆盖**。哪怕 `~/.gitconfig`
> 里已经指向了 GCM，前面那条 selector 依然会被调用一次。修法是在优先级最高的那层
> 写一条**空值**（空值会清空前面积累的全部 helper）再显式加一条 GCM。
> 实测：非仓库目录 `git credential fill` 从 `80s+` 超时 → **1 秒**；
> 真实推送从「30 次重试都不通」→ **第 1 次 6 秒成功**。
> 完整现场、两个顺手堵掉的隐患、以及为什么不用 `--system --unset`，
> 看 `推送脚本说明.md`。

> **前两次失败的真实原因（都已在脚本里处置）**
> - 第一次是两个原因叠在一起：地址配成了 `…/For-She.git`（GitHub 上不存在 →
>   `Repository not found`），而真实仓库 `She` 有个自动生成的 `Initial commit`
>   （地址就算改对，也会被 `rejected` 挡回来）。
> - 第二次是上面的网络超时。
>
> 脚本因此改成**先诊断、再推送**：单独测一次地址、把 git 的原始报错原样打出来、
> 按「找不到仓库 / 登录被拒 / 网络不通」分类给办法、推送前先问要不要覆盖远程，
> 并在网络类失败时自动重试。每次运行都会写一份 `推送日志.txt`（已进 `.gitignore`）。

**为什么是双击一个脚本，而不是敲命令：** 这台机器上装的是随工具附带的
**便携版 git** —— 它既不在系统 PATH 里（直接敲 `git` 会提示「不是内部或外部命令」），
也没有 Git Bash（那是装了 Git for Windows 之后才有的）。
`push-to-github.bat` 自己会去找 git，并用**脚本自身的位置**定位仓库目录，
所以它不依赖任何环境配置；它也**必须待在本目录里**，挪出去就认不到仓库了。

> 该文件不进仓库（已在 `.gitignore` 里）—— 它硬编码了本机便携版 git 的查找逻辑，
> 对别的机器没有意义。

它只编译、不签名、不跑模拟器。因为现在要的不是「App 跑起来了吗」，
而是「它编译得过吗」。**这一步是为了让真正的编译器说话 —— 静态通读
再仔细也替代不了它。** 免费额度足够（私有仓库每月 2000 分钟，
macOS runner 折合实际约 200 分钟 ≈ 40 次编译）。

> **新建一个记录不会再变成好几条。** 在补 21 屏时发现的：编辑器的 `@Query`
> 谓词在 `init` 里就定死成哨兵 id `"\u{0}__new__"`（为了绕开 `#Predicate`
> 捕获变量的限制），而 `Record.newID()` 生成的是随机 id —— 两者永远不相等。
> 于是插入之后 `record` 一直是 nil，**每改一次内容就走一次「新建」分支**，
> 每 0.8 秒的自动保存都再插一条。打字慢一点，列表里就会出现好几条几乎一样的记录。
> 改法是新建出来的那一条自己拿引用（`@State private var created: Record?`），
> 从头到尾只建一次。

> **首次启动不再写「示例数据」**。以前首次启动会插入一个叫「小满」的档案
> 和 4 条记录 —— 用户第一次打开 App，看到的是别人的女朋友，而
> 「她叫什么」这个问题一次都没被问过。现在首次启动走 `OnboardingView`（画布 15/16），
> 种子数据只在 SwiftUI 预览和 `-hi-seed` 启动参数下跑。

> **「配图」这条线在补 `PhotoStore` 之前是演出来的**：`PhotoGrid` 的「＋」往数组里塞的是
> `"hash:new0"` 这种假字符串，`PhotoCell` 画的是分类渐变，33 屏「换一张头像」的按钮体是空的，

**分享扩展**（`HerInfoShare/`，两个文件 360 行）—— 09 屏那一行原文是
「把她的原话分享进来，自动存成一条记录」。四个判断值得说明：

1. **分类由用户点，不由我们猜。** `Record.cat` 是必填的四值枚举，没有「未分类」；
   而「她这条算喜好还是在意的事」本身就是一次判断，猜错了留下的是**一条错数据**。
   所以面板上四个胶囊、必须点一个才能存 —— 与「打标是用户给的信号」是同一条纪律。
   面板上还有一句「存下来之后，分类和文字都还能改」，因为**现在不必想清楚**。
2. **扩展不写库。** 它只把内容丢进 App Group 里的收件箱（`HIShare.Inbox`），
   落成 `Record` 是主 App 在 `drainInbox` 里做的事 —— 与打标收件箱同一个模式。
   两个进程同时开一个 SwiftData 库会有写冲突，而扩展被系统回收的时机完全不可控。
3. **「自动」体现在不用手抄，不体现在替用户做判断。** 正文自动填、标题自动取首行
   （超 20 字截断 —— 这是记录卡标题在 375 宽里放得下的宽度；
   **首行是网址时标题取域名** —— `https://www.xiaohongshu.com/discovery/item/66f…`
   在列表里根本认不出来，域名一眼就知道是哪儿的；正文仍然一个字没少）。
   正文**一个字都不删**：面板上那行「原文 · N 字」就是在说这件事。
4. **面板用系统语义字体**（`.headline` / `.footnote`）而不是照抄 App 的固定字号 ——
   它是系统级面板，用户把系统字体调大时就该跟着变大。而主色与四个分类色
   仍取自共享契约，**一行 hex 都不写**（`check-swift.js` 会拦）。

> 这一块有两个「不报错、只是白做」的点，都写进交接文档与校验脚本了：
> ① `NSExtensionPointIdentifier` 必须是 `com.apple.share-services`
> （写成通知那个值 = 装得上、但分享面板里没有它）；
> ② `NSExtensionActivationRule` 是 `NSExtensionAttributes` 里的**一个 dict**，
> 那两条 `NSExtensionActivationSupports*` 是它的子键 —— **本工程第一次就是这么写错的**
> （少了外层那一层），被 `check-project.py` 第 5 段当场抓出来。
>
> 主 App 侧只在**真的落了东西**时提示一句「已存下分享的 N 条」（条数是数出来的，
> 不是写死的）。分享扩展存完就退场，用户在 App 里看不到任何痕迹 ——
> 而「刚才存下来了没有」正是分享之后最想确认的一件事。

> **四个入口（锁屏 / 快捷指令 / 长按图标 / 分享）走的是同一个模式**：入口只负责把东西
> 记下来（打标走 `notePendingMood`、分享走 `HIShare.Inbox.push`），
> 落库统一交给主 App 的 `drainInbox`。
> 好处不只是省事 —— 四处不会各写一套写库逻辑，`MoodSource` 也就不会有人在某一路上记错。
> 这也是为什么 `MoodSource` 里 `.shortcut` 与 `.quickAction` 是**两个值**：
> 它们看起来都是「系统级入口」，但一个是喊出来的、一个是按出来的，
> 出问题时排查方向完全不同，合成一个就再也分不清了。

**08 键盘工具栏 / 30 搜索筛选面板 / 07 历史版本对比** 这一轮做掉了。

> **08 键盘输入态**（`EditorView.swift` 的 `KeyboardActionBar`）落地时其实是两件事，只补了其中一件：
> **① 输入框加主色描边** —— `SField` 早就有聚焦态了（描边换主色 + 3px 主色 10% 光晕），
> 08 屏那句话不需要新代码；**② 键盘上方那排快捷胶囊** —— 这一轮补的。
>
> 那排胶囊**只能挂在 `placement: .keyboard` 上**，不能自己画一条钉在屏幕底部。
> 原型说明写得很准：「工具栏是键盘的附属条，不占用页面纵向空间，随键盘一起升降，
> 不需要单独控制显隐」。自己画的话，键盘一收起就会留下一条孤零零的空条 ——
> 那正好是 08 屏想避免的东西。
>
> 装的是「键盘弹起来之后够不到的那几个字段」。08 屏的内容区里，「记住这件事，
> 合适的时候提醒我」那一行正好被键盘顶出可视区 —— 所以「提醒」那枚不是快捷方式，
> 是**唯一的入口**。也正因为这个，顺手补了一条 `onChange(of: remindsMe)`：
> 拨完开关接着打字才落盘、拨完直接退就丢，那这个入口就是假的。
>
> **画布上的第四枚「记录时间」刻意没做。** 它不是漏了 —— 数据模型里只有
> `createdAt` / `updatedAt`（记录什么时候被写下），没有「这件事是什么时候发生的」这个字段，
> 03 / 08 两屏的字段区里也都没有它。补这一枚要先定义那个字段，而它会牵动
> **导出、版本快照、通知契约**三处。**留一个点了没反应的胶囊，比少一个更糟。**
> 相关验收在 `编译预检清单.md` 第 20 条。

> **09 / 10 情绪打标**（`MoodView.swift`）是「聊天里出现情绪关键词就提醒」那条路
> 在 iOS 上的**合规替代** —— 沙盒不允许读第三方聊天记录，所以情绪只能由用户自己给出。
> 两屏的分工很清楚：09 负责「给」，10 负责「给完之后顺手能做什么」。
>
> **两处最容易做错的地方：**
>
> ① **打标档位是三档，不是五档。** 模型里 `MoodLevel` 有五个（和锁屏通知那五个胶囊
> 一一对应），但 09 屏那排按钮只给三个。这是画布上的分法，不是遗漏：
> 手动那三个是「1 秒完成」的大按钮，多了就快不起来；而锁屏那一行要塞下五个胶囊，
> 位置决定它只能是五个。所以 `angry` / `calm` 只从锁屏来。
> 两处的**说法也是两套词**（`boardTitle`：挺好 / 有点累 / 心情差，vs 契约里的 `title`：
> 开心 / 累 / 低落 / 生气 / 平静）—— 合并成一个会让其中一处变得别扭。
>
> ② **10 屏的建议是「检索 + 排序」，不是模型生成的。** 页脚那行
> 「建议来自你记录过的内容 · 按更新时间排序」只有在真的这么做时才成立，
> 所以代码里一条写死的示例文案都没有：三条分别取「喜好里**最早**的」
> 「喜好里**最新**的」「讨厌的事里最新的」，并且**用记录 id 去重** ——
> 喜好只有一条时如实变成两条，面板上那个数字是数出来的，不是编的。
>
> **「2 小时后提醒我」要真的落一条提醒**再跳 05 —— 只跳过去、让用户自己再设一遍，
> 这个按钮就是句空话。所以它建的是 `repeatRule: .none`（仅一次）+ `leadMinutes: 0`（准时）：
> 那是「随手设一个」，不是「定一个长期提醒」，后者归 32 屏。
> 相关验收在 `编译预检清单.md` 第 21 条。

**06 / 24 / 28 / 29 原本也在这张清单上 —— 盘库存时发现它们已经落在地上了：**

- **06 空态** 在 `BrowseView`，而且做了两层判断：标题按**当前分类**换，三张起手卡
  只在**整个 App 一条都没有**时给。这不是同一个条件 —— 有 30 条记录的人切到空的
  「讨厌的事」，他要的是「换个分类看看」，不是被问一次「她爱吃什么」。
- **24 通知权限 · 关掉之后** 在 `SecondaryViews.swift`（`MARK: - 24`），
  并且顺手修掉了「通知被关、开关却显示开」那个逻辑矛盾。
- **28 搜索空态** / **29 回收站空态** 各是一处 `EmptyState`。

> 清单比实际落后一步是常态 —— **这本身就是「定期盘一遍库存」的理由**。
> 上面这四条不是新做的，是早就做完了、只是没被从待办里划掉。
> （这一轮我也差点犯反向的错：一开始把 08 写成「已被搜索独立成屏的设计规避」，
> 但画布上的 08 是**编辑器**的键盘态，和搜索页没关系 —— 那句结论下得太快了。）

> **07 历史版本对比**（`VersionHistoryView.swift`）比其余几屏多一层判断：
> 「恢复」不是回滚，而是**把那个旧快照落成一个新版本** —— 于是恢复前的内容原封不动
> 留在历史里，恢复这件事本身也可逆。页脚那句「当前内容不会丢失」不是安慰话，它就是实现方式。
> 差异则按**行**算，用计数池而不是最长公共子序列：一条记录本来就是几行字、顺序不会乱跳，
> 而且 LCS 会把「一句被改写」报成「删一行 + 加一行」两处噪声。
> 相关验收在 `编译预检清单.md` 第 16–17 条。

> **04 / 30 搜索与筛选**（`SearchFilterView.swift`）的关键不是布局，是**状态的所有权**：
> 搜索页上同时躺着三份「筛选」——25 屏的排序（长期偏好，写回设置）、
> 30 屏的条件（只活一次搜索）、以及搜索词本身。把 30 屏那份当成设置存起来，
> 用户会发现「我随手筛了一下，列表的默认排序被改了」。所以它刻意不落库，
> 而且**改词 / 换最近搜索 / 换分类都会自动作废**。
>
> 另一半是「按之前先知道有多少条」：面板底部那行数字与主按钮上的数字，
> 必须与列表**共用同一个 `accepts`** —— 各算各的迟早会对不上，
> 而「按之前说 3 条、按下去出 5 条」比不给预览更伤信任。
> 验收在 `编译预检清单.md` 第 18–19 条。

> **06 / 21 一起做掉了**，因为它们本来就是同一条线：06 的三张起手卡
> 点进去就是 21 那个预填好的编辑器。中间那层判断是
> 「**替他填一半，不替他写**」—— 标题替他定了，「标题」这个字段最容易卡住人；
> 而正文一个字都不预填，只给一条灰色示范当 placeholder，
> 因为预填的正文会被当成「标准答案」，用户要么照抄要么删干净重写，两种都比空白更费事。

> **照片字段只在编辑态出现**（03 / 21 两个新建态都没有，只有 34 有）。
> 也就是说：新建时先把话记下来，照片是之后从记录详情页点「编辑」回来补的。
> 这是画布三处一致给出的规则，但**它意味着新记录没法一步就配上图** ——
> 如果你想改成「新建时也能加图」，把 `EditorView` 里那个 `if isEditing`
> 去掉就行，一行的事。

> 14 / 36 锁屏通知、09 屏的四个系统级入口**都不在这份清单里** —— 它们是这套骨架里
> 需要动工程配置的部分（**三个 target**：主 App + 通知扩展 + 分享扩展、**两份共享契约**、
> **三份 Info.plist**、App Group 一处、主 App 侧若干处接线）。
> 想核对「哪个键漏了会白做」，看交接文档的「通知内容扩展」与「分享扩展」两章。

先回头看设计，别急着加组件。**

## 四、三处设计稿与 iOS 的差异（重要）

### 1. 字体：中文用系统，数字用 SF Pro

设计稿是 `Noto Sans SC` + `Inter`。到了 iOS：

- **中文直接用 `.system`（苹方）**。它是 iOS 上渲染质量最好的中文字体，
  而且自带系统级字重与动态字距。强行捆绑 Noto Sans SC 三个字重大约多 15MB 包体，
  换来的是一套略逊于系统的中文 —— 不划算。
- **数字用 SF Pro + `.monospacedDigit()`**。Inter 与 SF Pro 在数字上差异极小，
  而等宽数字是必须的：`20:00` 这类时间、`128 条` 这类计数，
  不设等宽的话数字一变宽度整行都在跳。

真要跨平台一致（比如同时出 Android），再走捆绑字体方案 —— **Token 层已经收口，只改一个文件**。

### 2. 图标：手绘 SVG → SF Symbols

底部 4 个 tab 图标在设计稿里是手绘 SVG，代码里换成
`house` / `square.grid.2x2` / `magnifyingglass` / `bell`。
理由：自动跟随字号与字重、矢量不用切图、且是系统自身的语言。
其余手绘图标同理优先找 SF Symbols 对应项，找不到的再导出 SVG 当资产。

### 3. 地理围栏：**20 是硬上限**

iOS 单个 App 最多监听 20 个 `CLCircularRegion`。这不是可调参数 ——
它已经改变了设计（05 屏要显示「已用 3/20」，加满后只能关一个才能再加）。
所以 `ReminderService.maxGeofences` 写成常量，且到顶时不静默失败。

## 五、这份代码的诚实说明

**它没有在 Xcode 里编译过。** 开发这个骨架的环境是 Windows，
没有 Xcode 与 iOS SDK —— 这不是偷懒，是 Apple 的硬约束：
Xcode 只跑在 macOS 上，交叉编译到 iOS 也不合法。

所以分两层说清楚：

**已经做过的（静态层）** —— 七份校验脚本，全部通过：

| 脚本 | 管什么 |
|---|---|
| `check-swift.js` | 括号配平、类型引用闭合、Route 与导航对齐、关键常量落地（17 项） |
| `check-argorder.py` | 逐成员 `init` 的**标签顺序**必须与属性声明顺序一致（33 个类型 / 67 处调用） |
| `check-project.py` | `project.yml` 路径自洽、两份 plist 合法、**跨文件契约一致性**（分类 id / App Group） |
| `check-guide.py` | 操作指引与推送脚本自洽：路径存在、`.bat` 是 CRLF + **GBK 字节**、标签无悬空（46 项） |
| `check-handoff.js` | 交接文档 12 章齐全、37 屏逐条、验收清单 |
| `check-prototype.js` / `check-spec.js` | 设计侧两份 HTML 交付物 |

> `check-swift.js` 里的「共用色只有一个定义处」这条判据，扫的是**剥掉注释之后的代码**。
> 注释里写 hex 是在解释「这里为什么不再抄一遍」，那不是副本；而**字符串里**的 hex
> 是真副本（导出 CSS / PDF 时最容易这么写），仍然会被抓出来。这条判据本身
> 也做了正反例自测 —— 否则分不清「不报了」和「永远不报了」。

逐行通读 5524 行之后，把能确定的都改掉了（22 类），其中：
`ForEach(modes, id: \.0)` 这种 KeyPath 指元组元素的写法、`add()` 缺 `try/await`、
有 `private` 存储属性导致逐成员 init 整体降级为 private、
tab 根屏对空 `path` 调 `removeLast()` 会直接 `fatalError`。

**还没有做过的（编译器层）** —— 以下三类**必须要真机编译才能发现**，
在 `编译预检清单.md` 里每类都给了两种修法：

1. `#Predicate` 宏对捕获变量的限制（我按最保守的写法处理了，但宏的行为只有编译器知道）
2. Swift 6 严格并发下 `UNUserNotificationCenterDelegate` / `CLLocationManagerDelegate`
   的 `nonisolated` 标注（已按 iOS 17 的 async 版本写，但可能有 actor 隔离告警）
3. `FlowLayout` 自定义 `Layout` 的边界情况

预计首次编译会有若干警告与少量错误，都在上面这三类里。
**走「路线 A」把日志拿回来，就能把这三类一次性收掉。**

**其中最容易悄悄失败的是通知扩展**，因为它的失败方式不是报错：
分类 id 对不上、`UserInteractionEnabled` 没写 `true`、`CFBundlePackageType`
不是 `XPC!`，结果都只是「通知照弹，长按展开回到系统默认样子」。
所以这几个键在 `Info.plist` 里都加了注释，`check-project.py` 会守住它们，
交接文档里也单列了一张表。
