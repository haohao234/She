操作指引 · 四步拿到编译结果

怎么让编译器说话

你的机器是 Windows，而 Xcode 只跑在 macOS 上 —— 这是 Apple 的硬件约束，绕不过去。 所以编译这件事交给云端的 macOS 机器做，只把报错清单带回来给我。 好消息是：本地能做的部分我已经全部做完了，你剩下四步。

0 / 4 已完成

先看清楚：本地已经就绪的东西

这些不需要你动手，列出来是为了让你知道「推上去的就是这份状态」。

✓
本地 Git 仓库已建好她的信息本-iOS/ 已 git init，分支 main，27 个文件已提交，工作区干净
✓
工程结构已声明化project.yml —— 两个 target、共享契约、App Groups 全在里面，不用手工建 target / 拖文件 / 勾 Compile Sources
✓
云端流水线已写好.github/workflows/ios-build.yml —— 只编译、不签名、不跑模拟器，并自动把 error / warning 摘成清单
✓
五份校验脚本全绿原型 13 项 · 规范页 16 项 · 交接 9 项 · Swift 17 项 · 工程层全通过
✓
两份 Info.plist 的关键键已补齐包括扩展缺了「连进程都不会起」的 CFBundlePackageType，和主 App 那份原本根本不存在的 plist
▶
一句话：代码、工程声明、流水线都是现成的。你要做的只是「把它放到 GitHub 上，让云端的 Mac 编译一次」。

STEP 01 建一个空的远程仓库

1

在 GitHub 上新建仓库

只需要点几下，30 秒

打开 github.com/new（没有账号就先注册，三分钟）。填两处：

Repository name纯 ASCII，例如 herinfo-ios
别用中文。路径里的非 ASCII 字符会让后面 xcodebuild 的报错行更难解析
VisibilityPrivate（推荐）
私有仓库每月有 2000 分钟额度，macOS 机器按 10 倍计费 → 约 200 分钟，够跑 40 次左右。这个项目是私事，不值得为省额度公开
⚠
三个勾全部不要勾 —— Add a README file、Add .gitignore、Choose a license。 勾了远程仓库就会先有一个提交，本地又没有，push 时会被直接拒绝（报 non-fast-forward）。 我们要的是一个完完全全的空仓库。

建好后页面会给你一段示例命令，不用照着做 —— 下一步的命令是给它准备好的。

STEP 02 把代码推上去

2

关联远程并推送

两条命令，复制粘贴到 Git Bash

打开 Git Bash（开始菜单搜「Git Bash」），粘贴下面两行。第一行里的 URL 换成你刚建的那个仓库地址。

# ① 进入仓库目录（本地仓库已经建好，不需要再 init）
cd "D:/workbwenjian/2026-09-10-14-54-12/她的信息本-iOS"

# ② 关联远程仓库 —— 把 URL 换成你自己的
git remote add origin https://github.com/你的用户名/herinfo-ios.git

# ③ 推上去
git push -u origin main
⚠
仓库根目录必须是 她的信息本-iOS/ 本身，不能是它的上一层。 如果你把整个工作区推上去，.github/workflows/ 就不在仓库根目录了 —— Actions 会毫无反应，而且不报任何错，它只是「没找到工作流」。这是最容易踩的坑。
▸
首次 push 会弹窗要你登录 GitHub（Git Credential Manager，浏览器授权一下就行）。 万一弹的是「用户名 / 密码」框：GitHub 早就不收密码了， 密码栏要填 Personal Access Token（github.com/settings/tokens 新建，勾 repo 权限）。

设计稿不用推 —— 流水线只编译 她的信息本-iOS/ 这一份目录。

STEP 03 等云端的 Mac 编译完

3

看 Actions 面板

推上去之后它会自己开始，3–5 分钟

回到你的仓库网页，点顶部 Actions 标签。会看到一条叫 「iOS 编译检查」的运行记录 —— 名字前面有个小黄点表示正在跑，转圈变绿或变红就结束了。

✓ 绿了

  • 说明 0 error，骨架能编译
  • 点进去看「摘出错误与警告」那一步，会列出若干 warning
  • 把 warning 也贴回来 —— 它们多半就是预检清单第 3 节那三类

✕ 红了

  • 这正是我们要的结果 —— 它换来了一份真实报错清单
  • 点进失败的运行，展开 「摘出错误与警告」那一步
  • 那一步不会因为是失败就不跑，它是专门为此写的
◦
几个可能让你以为「没跑」的情况：推送后要等几秒 Actions 页面才出现记录； 免费机器可能要排队，显示 Queued 是正常的； 想重跑不用改代码 —— 页面右上角 Re-run all jobs， 或左侧 iOS 编译检查 → Run workflow 手动触发。

STEP 04 把报错贴回来给我

4

复制那两段，扔进对话里

不用整理，原始输出就行

只要「摘出错误与警告」那一步的两段内容，长这样：

==========================================
 错误（error）
==========================================
# 真实输出里这行开头是完整路径
#   /Users/runner/work/herinfo-ios/herinfo-ios/  ← 这一段，这里简写了
.../HerInfo/Features/HomeView.swift:142:23: error: cannot find 'xxx' in scope
.../HerInfo/Services/ReminderService.swift:88:9: error: value of type ...

==========================================
 警告（warning）
==========================================
.../HerInfo/Features/EditorView.swift:61:5: warning: main actor-isolated ...

------------------------------------------
error 总数：2
warning 总数：11
要贴的整个 error / warning 段落，保留 文件:行:列 那一段
更值钱的note: 补充行 —— Swift 的类型推断与并发报错全靠 note 定位，它比 error 行本身更有用
不用贴3000 行完整构建日志。真需要我会让你下载 artifact（流水线保留了 14 天）
▸
然后我做什么。按行改 → 重跑 check-swift.js（17 项）+ check-project.py 保证不回归 → 你再推一次。 如果报错落在预检清单第 3 节的三类之外，那是真错误，同时也说明我的静态判据漏了一类 —— 我会把新判据补进脚本，让下一轮不用再靠人眼通读 5524 行。 只出现那三类的话，通常一轮就收敛。

PLAN B 如果 GitHub 打不开

GitHub 在国内时快时慢。如果你连仓库都建不上、或者 git push 一直超时， 别在这上面耗 —— 换下面任一条。

走代理 如果你本机有代理，给 Git 单独配一次即可：
git config --global http.proxy http://127.0.0.1:端口
和你平时浏览器用的那个端口一致
Codemagic 专做移动端的云 CI，注册后可以直接上传项目压缩包，不一定要走 GitHub。免费额度 500 分钟/月。 代价是要在它那边重新配一次构建命令 —— 需要的话我来写它的配置文件。
找一台 Mac 借朋友的、或租一台云 Mac（按小时计费）。
在这台 Windows 上装 macOS 是违反 Apple 许可协议的，而且极不稳定 —— 我不建议把项目押在这上面。
◦
注意：Gitee（码云）虽然国内快，但它的流水线不提供 macOS 机器， 所以想省掉 Mac 这件事上它帮不上忙。

AFTER 编译过了之后

编译通过只是个门槛，过了之后还有三件事，按优先级：

1在模拟器里跑一次主流程
预检清单第 6 节列了必过的 5 条 —— 添加记录、分类浏览、搜索、设置链、导出。
2真机验那两条跨进程验收
第 13 条「通知长按展开」和第 14 条「锁屏打标」—— 这是整套交付里唯一跨进程的部分，失败方式很安静，值得单独花时间。
3铺开剩下 13 屏
它们用的是已经在 Components.swift 里的组件，属于同一模式的重复劳动，不是新判断。

总结成一句话

建一个空仓库（三个勾都别勾）→ 在 她的信息本-iOS 目录里 git remote add 再 git push → 等 Actions 跑完 → 把 error / warning 两段贴回来。

卡在任何一步，把屏幕上的字贴给我就行。
