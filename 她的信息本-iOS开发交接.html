这份文档的作用是把「设计稿上的 37 屏」翻译成「iOS 工程师能直接开工的一套结论」。 它不替代设计规范页 —— 令牌、组件、数据模型的权威定义在规范页， 这里只讲这些设计如何在 iOS 上落地，以及落地时会撞到的边界。

一句话结论

SwiftUI + SwiftData，最低 iOS 17，零第三方依赖。 数据全部落本机，没有账号也没有云同步 —— 这不是省事，这是这个产品的隐私承诺，取消它产品就没了意义。

骨架覆盖到哪

主流程 01→02→03→04→05、本轮新增的 32/33/34/35、 以及 36 锁屏通知展开态（含 Notification Content Extension 独立 target） 已写成真代码；设置链 12→35 / 12→27 / 12→13→23 也接上了。 其余 13 屏是同一模式的重复劳动，照写即可。

先读这一条：交接用的代码骨架没有在 Xcode 里编译过（编写环境没有 Xcode 与 iOS SDK）。 静态检查（括号配平、类型引用闭合、符号去重、路由落点、两份 plist 与跨文件契约一致性）全部通过， 但 #Predicate 宏的捕获限制、Swift 6 严格并发下的 nonisolated 标注、自定义 Layout 的边界情况， 这三类只有真机编译才能暴露。预计首次编译会有若干警告与少量错误，都在这三类里。

拿到编译结果的成本已经压到最低：工程结构由 project.yml 声明（不需要手工建 target）， 并且配好了 GitHub Actions 流水线 —— 把目录推上去就能换回一份真实的报错清单， 不需要自己有一台 Mac。详见「还差什么」那一节。
Stack

技术选型

每一条结论都附了理由，理由比结论更值得复核 —— 如果理由不成立，结论就该改。

选择结论为什么
UI 框架 SwiftUI 37 屏里绝大多数是「卡片 + 列表 + 表单」，没有复杂动画与自绘。SwiftUI 在这个形状上的开发速度是 UIKit 的两倍以上，而且深浅色、动态字体是免费的 —— 这个 App 两个都要。
数据层 SwiftData 模型只有 6 张表、关系简单、无多端同步需求。@Query 直接驱动列表，省掉一整层 ViewModel 样板。代价是最低版本锁到 iOS 17。
最低版本 iOS 17.0 SwiftData 与 Layout 协议的门槛。降到 16 要换回 Core Data，改动量约等于重写数据层 —— 除非产品明确要求覆盖 iOS 16 机型，否则不值得。
依赖 零第三方 不引任何包管理器。所有图标走 SF Symbols、字体用系统、导出用系统框架。少一个依赖就少一个「明年没人维护」的风险，这对一个要放很多年的私人工具尤其重要。
数据存放 纯本机 无账号、无云同步、无分析 SDK。图片只存沙盒 + 记 hash。这不只是技术选择 —— 它是 16 屏那句「不读取聊天记录」的同一件事。
并发 Swift 6 严格并发 数据层与 UI 都在 @MainActor；通知与定位的 delegate 标 nonisolated 后回调回主线程。数据量小，不需要后台上下文。

Tokens

令牌落地

设计规范页里的 16 个令牌，在代码里是 16 个 Color 静态属性， 每个声明浅色与深色两个字面值，通过 UIColor(dynamicProvider:) 跟随系统外观。

Tokens.swift · 双档动态色
/// 声明一个跟随系统外观切换的语义色。
static func dual(_ light: UInt32, _ dark: UInt32) -> Color {
    Color(uiColor: UIColor { trait in
        trait.userInterfaceStyle == .dark
            ? UIColor(hex: dark)
            : UIColor(hex: light)
    })
}

enum C {
    static let bg      = Color.dual(0xF8F5F0, 0x1A1613)   // 页面底
    static let card    = Color.dual(0xFFFFFF, 0x241F1B)   // 卡片面
    static let primary = Color.dual(0xC0614A, 0xD37C63)   // 主色
    static let ink     = Color.dual(0x1F1E1B, 0xF3EEE8)   // 主文字
    static let danger  = Color.dual(0xB0523C, 0xD98672)   // 危险色 ≠ 主色
    // …共 16 个，与规范页逐值对应
}

为什么不用 Asset Catalog 的 Color Set

两者都能跟随深浅色。用代码的版本零配置就能跑（拖进 Xcode 直接编译）， 且 16 个色值集中在同一个文件里，设计师对着规范页改一处即可。 如果团队更希望「改色不改代码」，换成同名的 Color Set 就行 —— 视图层一行都不用动，因为大家用的都是 C.primary 这样的语义名。

三条不能违反的规则

  • 视图文件里不许出现字面色值。看到 Color(red:…) 就是错，回 Token 层加一个语义名。
  • 危险色永远不等于主色。删除是破坏性动作，它和「保存」同色的话，用户就没法靠颜色区分两件事。
  • 圆角一律 .continuous。iOS 的连续曲率圆角（俗称超椭圆）和 CSS 的 border-radius 不是同一条曲线 —— 默认的 .circular 看起来会更硬、更廉价。

字体：这是设计稿与 iOS 之间最大的一处差异

设计稿是中文 Noto Sans SC、数字与字母 Inter。到 iOS 上要分开处理：

角色设计稿iOS 落地理由
中文 Noto Sans SC 系统字体
.system(size:weight:)		 系统字体就是苹方，是 iOS 上渲染质量最好的中文字体，自带系统级字重与动态字距。捆绑 Noto Sans SC 的三个字重（Regular / Medium / SemiBold）大约多 15MB 包体，换来的是一套略逊于系统的中文 —— 不划算。
数字 / 字母 Inter SF Pro + .monospacedDigit() Inter 与 SF Pro 在数字上的视觉差异极小。而等宽数字是必须的：20:00 这类时间、128 条 这类计数，不设等宽的话数字一变宽度整行都在跳。

逐屏规格

37 屏逐个过一遍。右边是这一屏会用到的系统能力 —— 没有标 API 的就是纯排版，照组件库拼即可。 带主色边框的五条是本轮新增，也是「屏齐了」与「能用」之间最后的那段路； 其中 36 屏是 14 屏那条通知的长按展开态，要单建一个 target（见「通知内容扩展」）。

主流程 · 6 屏

01
首页 · 她的档案
顺序是「问候 → 搜索条 → 她的名片 → 最近的提醒 → 四条分类」。首页只回答一个问题：今天有什么是她相关的。所以提醒只列最近会发生的那一条，不是全部 —— 首页是看一眼就走的地方。

02
分类浏览 · 喜好
四个分类胶囊横排，一屏之内不用退出就能换一类。列表项左侧有 3px 分类色条，靠颜色就能扫过去。右下角浮起按钮离屏底 108，不是贴底 —— 贴底会被底部导航压住一半。
纯 UI@Query@AppStorage
03
新增记录 · 自动保存
自动保存是状态条不是进度条：只说「已自动保存」+「本地版本 N」，不报条数、不问评分、不显示「还差几条」。记录一旦变成任务就没人愿意记。改动后 0.8s debounce 落盘，每次落盘版本 +1。
纯 UISwiftDataTask.sleep
04
搜索 · 全局查找
搜标题与正文。首页那条搜索栏是按钮不是输入框 —— 点它进这一屏再打字，这样首页不会被键盘顶起来。

新建提醒 · 定时与场景 本轮新增
三处落地要点：①「时间」与「提前多久」是两组 —— 前者是事实（每周三 20:00），后者是你想要的余量（提前 10 分钟），混在一起用户算不清几点响。 ②「通知预览」是表单最后一块，保存前能看见那行字 —— 提醒的成败全在它身上。 ③ 定时/场景整体换块，不在同一组里加可选字段（那会让表单变成一半字段是灰的）。 提前量落到系统里就是「触发时刻 −N 分钟」。

32 屏脚注承诺「点开直接回到这条记录」。落地是：通知的 userInfo 里带 recordID， delegate 收到点击后 post 一个通知，RootView 监听它来推路由。

ReminderService.swift · 点通知 → 跳记录
// 发出时：把 recordID 塞进去
content.userInfo = ["recordID": rid]

// 收到点击时：交给 RootView 推路由
nonisolated func userNotificationCenter(
    _ center: UNUserNotificationCenter,
    didReceive response: UNNotificationResponse
) async {
    let info = response.notification.request.content.userInfo
    guard let rid = info["recordID"] as? String else { return }
    await MainActor.run {
        NotificationCenter.default.post(name: .openRecord, object: rid)
    }
}

三条纪律

纪律做法不做会怎样
契约只写一遍 Shared/NotificationContract.swift 同时属于两个 target 的 Compile Sources， 且只依赖 Foundation 与 UserNotifications（不 import SwiftData / SwiftUI）。 分类 id、动作 id、userInfo 的键、App Group 名、五个情绪档、12 个共用色值，全在这里。
在 project.yml 里，这个「同时属于」是写死的： 同一个路径出现在两个 target 的 sources 下 —— 手工勾漏一个的可能性被消除掉了。 		两边各写一遍就一定会分叉 —— 而分叉的表现是 「通知照常弹，长按展开是系统默认样子」：不报错、不崩溃，只是白做。
打标走单向收件箱 扩展只往 App Group 里 push； 主 App 启动 / 回前台时 drain 出来，落成真正的 Mood 行（来源标成「锁屏」）。 两个进程同时开一个 SwiftData 库会有写冲突，而扩展被系统回收的时机完全不可控 —— 在那种地方做数据库事务是不负责任的。方向只有一条，也就没有并发问题。
图片让系统搬 主 App 挂 UNNotificationAttachment， 系统把文件拷进通知自己的目录，扩展直接读 attachments.first.url。 走共享容器就得多管一套「谁创建、谁清理、什么时候过期」的逻辑， 而扩展读图根本不需要它。

契约长什么样

Shared/NotificationContract.swift
// 两个 target 的 Compile Sources 都要勾上；只 import Foundation + UserNotifications
enum HINotify {
    static let appGroup = "group.com.herinfo.app"
    static let reminderCategory = "HI_REMIND"   // 必须与扩展 Info.plist 逐字一致

    enum Action { snoozeOneHour, doneToday }        // 收起态只放两个轻决定，刻意的
    enum Mood: String, CaseIterable { happy, tired, down, angry, calm }
    enum Primary { light, dark, softLight, softDark, deepLight, deepDark }
    enum Cat: String { like, trait_, care, hate }   // 每个都有 lightHex + darkHex + title

    struct Payload { /* recordID / title / body / cat / version / photoCount */ }
    struct MoodMark: Codable, Sendable { /* recordID / level / at */ }

    enum Inbox {                                    // 扩展 → 主 App 的单向通道
        static func push(_ mark: MoodMark)          // 扩展侧只写
        static func drain() -> [MoodMark]           // 主 App 取走并清空
    }
}
收起态为什么什么都不画：扩展的 SwiftUI 视图在收起态被系统压得很矮。 这时候如果还画图或画一排胶囊，收起的样子就变成「一条被切掉一半的怪东西」。 所以 36 屏的视图里，非展开分支直接 Color.clear.frame(height: 0) —— 画布 14 屏（收起态）能逐字对得上，靠的就是这个分支。

主 App 侧要接的六件事

  • 排程时写 content.categoryIdentifier = HINotify.reminderCategory —— 不写，扩展永远不出现
  • userInfo 里塞 recordID / cat / version / photoCount —— 缺字段时扩展会退到系统画的那份内容，宁可少画一块，也不整块空白
  • attachFirstPhoto(of:to:) 挂附件 —— 扩展读图靠它，不需要共享容器
  • registerCategories() 注册 HI_REMIND + 两个动作 —— 收起态的按钮在这里定义
  • HerInfoApp 启动 / 回前台 drainMoodInbox(into:) —— 打标落库的唯一入口
  • 两个 delegate 方法标 nonisolated，只取 Sendable 纯值再跨界 —— Swift 6 严格并发下不这么写编译不过
色值的单一真相处：主色三档与四个分类色要在三个地方一模一样 —— 屏幕上是动态色、锁屏通知上是深色档、导出的 PDF 上是浅色档（打印语义，不跟随主题）。 所以那 12 个 hex 全部上提到 HINotify， App 的 Tokens.swift 与 ExportService 都改成引用它， NotificationStyle.swift 里一个 hex 都不留。 静态检查守着这条线：契约之外出现任何一个共享 hex 就算失败。
Model

数据模型

6 张表。字段定义以规范页「数据模型建议」为准，这里只讲从 JSON 变成 SwiftData 时做的三个决定。

① 版本号长在记录上

不放历史表里。这样列表页不用 join 就能显示「第 12 版」。

② 历史版本存整份快照

不存 diff。记录本来就是几十个字，省下的空间远远抵不过「读一条历史要重放整条链」的复杂度。

③ 图片只存 hash

路径会随重装/换机/系统清理失效，hash 不会；存 URL 则意味着图片在别人服务器上。

Redlines

技术红线

前两条是平台边界，不是技术选型建议。它们直接改变了两个功能的做法， 所以必须写进交接；后两条是这套设计对用户做的承诺，各需要一个真的会执行的机制兜住。

① iOS 沙盒不允许读第三方聊天记录

已改设计

原方案「聊天出现情绪关键词就提醒」没有任何合法路径。已改成：手动打标 + 系统级入口 —— 长按图标 / 快捷指令 / 分享扩展 / 通知上直接选档位。

这条的分量：它把一个「平台能力问题」转成了「用户动作问题」——不猜、不读，只记录用户自己给出的判断。

② 地理围栏有数量上限

已加额度提示

iOS 单 App 最多监听 20 个 CLCircularRegion（Android 后台定位同样有配额）。 所以场景提醒不能做成「想加多少加多少」。

落地要求：开关式管理 + 数量上限 + 到顶时给提示。静默失败是最坏的一种 bug。

③ 数据不出本机

无账号、无云同步、无分析 SDK、无崩溃上报。图片落沙盒且只记 hash。 导出的文件落「文件」App，用户能自己删。

怎么兜住：不引入任何网络依赖（包括埋点）。这一条一旦破例就再也回不去了。

④ 删除要能收尾

删除是软删除，回收站留 30 天，「清空」才算真删（且要过二次确认）。 但后台任务不保证按时执行 —— 所以清理必须是「下次打开时顺便做」。

怎么兜住：BGTaskScheduler 兜底 + 启动时补跑一次，两条路都要有。

还差什么

剩下 13 屏是同一模式的重复劳动，不是新判断。之所以这么判断，是因为它们用的组件 —— 卡片 / 胶囊 / 开关 / 空态 / 确认面板 —— 都已经在 Components.swift 里了。

但第一件该做的不是补屏，是先让它编译起来

骨架没有在 Xcode 里编译过 —— 编写环境是 Windows，而 Xcode 只跑在 macOS 上。 这不是能靠努力绕过的限制，是 Apple 的硬约束。静态通读再仔细，也替代不了编译器。 所以工程已经配好了两条路：

路线怎么做适合
A · 不用 Mac 把 她的信息本-iOS/ 整个目录推上 GitHub， .github/workflows/ios-build.yml 会自动跑 xcodebuild，并把 error / warning 摘成清单回在日志里。 现在的目标就是拿到报错清单，不需要模拟器
B · 有 Mac brew install xcodegen && xcodegen generate 就有了工程，不用手工建 target / 拖文件 / 勾 Compile Sources / 加 App Groups —— 那些都在 project.yml 里声明好了。 要看画面、要真机跑、要调试
预计首次编译会有若干警告与少量错误，集中在三类： #Predicate 宏捕获限制、 Swift 6 严格并发下的 nonisolated 标注、 自定义 Layout 边界 —— 每类在 编译预检清单.md 里都给了两种修法。 把日志贴回来按行改即可。

照搬即可的那批 · 已全部落地

  • 原先列在这里的 30 筛选面板（SearchFilterView.swift）、 07 历史版本对比（VersionHistoryView.swift）、 08 键盘工具栏（EditorView.swift 里的 KeyboardActionBar）， 以及 06 / 24 / 28 / 29 都已经写好
  • 08 的第一句提醒：那排胶囊只能挂在 placement: .keyboard 上， 不能自己画一条钉在屏幕底部。原型说明把这句讲得比文档还准 —— 「工具栏是键盘的附属条，不占用页面纵向空间，真机上它随键盘一起升降」。 自己画的话，键盘一收起就会留下一条孤零零的空条，而那正是 08 屏想避免的东西
  • 08 的第二句提醒：它装的是「键盘弹起来之后够不到的那几个字段」。 内容区里「记住这件事，合适的时候提醒我」那一行正好被键盘顶出可视区 —— 所以「提醒」那枚不是快捷方式，是唯一的入口。 也正因为这个，顺手补了一条 onChange(of: remindsMe)： 拨完开关接着打字才落盘、拨完直接退就丢，那这个入口就是假的
  • 08 还差一枚「记录时间」，是故意没做：数据模型里只有 createdAt / updatedAt （记录什么时候被写下），没有「这件事是什么时候发生的」这个字段， 03 / 08 两屏的字段区里也都没有它。补这一枚要先定那个字段， 而它会牵动导出、版本快照、通知契约三处 —— 留一个点了没反应的胶囊，比少一个更糟
  • 07 的一句提醒：差异按行用计数池算（不取最长公共子序列）， 「恢复」是把旧快照落成一个新版本、不是回滚 —— 所以恢复前的内容仍在历史里，恢复本身也可逆
  • 30 的一句提醒：搜索页上有三份「筛选」——25 屏的排序是长期偏好（写回设置）， 30 屏的条件只活一次搜索。把后者当设置存起来，用户会发现 「随手筛了一下，列表的默认排序被改了」；所以它一改搜索词就自动作废
  • 面板里那行条数不是装饰：它和主按钮上的 N 必须与列表 共用同一个判断，否则「按之前说 3 条、按下去出 5 条」比不给预览更伤信任

需要额外工作的（1 项）

  • 09 / 10 情绪打标 —— 落标本身简单，但要建 App Intent 与 Share Extension 两个独立 target。 这块的价值全在「入口够不够顺手」上，值得单独排一期。
14 / 36 锁屏通知已经不在这张清单里了。 两个 target 的代码、共用的契约文件、Info.plist 的六个键、 以及主 App 侧的排程与收件箱对接都已写完， 连「哪个键漏了会白做」都写进了下一节。剩下的是编译，不是设计。
判断标准：照搬时如果发现某一屏需要「新写一个组件」， 多半意味着那一屏用了别人没有的样式 —— 先回头看设计，别急着加组件。

验收清单

按这个顺序自测，前 6 条通了就算「主流程可用」。 后面几条是这套设计里最容易做走样的地方，逐条对着设计稿核。

#验收项通过标准
01首次启动写种子数据，首页四个分类都有数、名片显示「在一起 N 天」
02新建记录 → 自动保存打字 0.8s 后状态条变「已自动保存」，版本号 +1，杀掉进程重进内容还在
03记录配图图片紧跟标题；一行正好 3 个；到 9 张后添加格消失
04新建提醒 → 通知到达通知上那一行字与 32 屏「通知预览」逐字一致；点开直接落在那条记录
05提醒提前量设「20:00 · 提前 10 分钟」，实际是 19:50 响
06重启后提醒还在杀掉进程重进，提醒仍会按时到达（启动时重排生效）
07深色模式切系统深色，37 屏全部跟着变；开关的「开」态不变灰
08删除与恢复删除 → 列表消失 → 回收站能找到 → 恢复后回到原位
09导出过面容 ID；三种格式都能打开；JSON 里的 id 与记录一致
10权限被拒的降级系统里关掉通知权限，24 屏给出说明并可跳系统设置，不假装还能用
11无网络飞行模式下全流程可用（全本地，没有任何一处需要联网）
12字号放大辅助功能里放大字号，文字不裁切、卡片不重叠
13通知长按展开展开后能看到配图 + 分类点 + 「第 N 版」+ 五个胶囊；收起态仍是系统原生样子，没有多余留白或半截胶囊
14锁屏打标点一个胶囊 → 变成「已记下」；这次打标进共享收件箱，下次打开 App 时写进她的档案（来源 = 锁屏）· 期间 App 从未被启动
第 4 条和第 6 条最容易被跳过，但它们是这个产品唯一真正的功能。 记录只是手段，「合适的时候被想起来」才是它存在的理由。 如果提醒不可靠，前面 36 屏做得再细也没有意义。
第 13 / 14 条是这套交付里唯一跨进程的部分 —— 它们的失败方式很安静：通知照弹，只是长按展开回到系统默认样子， 没有任何报错。所以这两条要手动过，不能只信编译通过。
